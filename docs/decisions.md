# Architecture Decisions

- **决策 1: 试卷切分采用“本地优先 + 结构异常模型回退”**
  - *原因*: 正常固定结构试卷无需 API；共享质量门发现结构性 WARN/FAIL 时，仅重切异常试卷可兼顾成本与可靠性。PASS* 尾部粘连不触发回退。
- **决策 2: GUI 架构重构，解耦 API 依赖**
  - *原因*: 方便普通老师在无 Key 的情况下进行本地切分验收与调试，同时降低开发者的测试成本。
- **决策 3（已废弃，见决策 5）: Word 使用按用途区分的 Pandoc reference DOCX**
  - *原因*: Pandoc 默认 Word 样式无法稳定保证 A4、中文字体、标题层级、列表缩进和页码；三套模板分别服务学生训练、教师讲义和答案核对。

- **决策 5: 题目原文改为「克隆原卷 OOXML」，不再重新排版；移除 Pandoc**
  - *原因*: 重新排版这条路走不通——原卷的格式在 `extract_docx_text` 就被压成纯字符串了，实测 100% 的段落带 `pPr`、100% 的 run 带 `rPr`，全部被丢弃；插图更是**永久丢失**（导出的 docx 里 media 数量为 0，湖北卷 8 张图全没了）。经 Markdown 中转还引入两个 bug：整篇阅读被压成一个 10008 字符的段落；`____36____` 被 Pandoc 当成 `__strong__` 把正文随机加粗。
  - *做法*: 复制原 docx 整个压缩包，只把 `document.xml` 的正文换成被选中题目的原始 `w:p`/`w:tbl` 节点。跨卷合并交给 `docxcompose` 处理样式/图片 ID 冲突（三份样卷有 17 个冲突 styleId、10 个冲突 rId，不重映射会静默出错）。
  - *代价*: 放弃了「CLI 零 pip 依赖」这条约束——但它事实上早已被 Pandoc（一个未声明的系统二进制）破坏。用 pip 包换掉系统二进制，对打包成 macOS 应用是净收益。
  - *验证*: 导出结果的加粗/下划线/斜体/插图/表格数量与原卷对应段落**逐一相等**。
- **决策 4: 输入与输出清空必须独立并确认**
  - *原因*: 目录清理属于破坏性操作，必须显示路径和文件数量，并限制在项目内的非保护目录。

- **决策 6: 答案区边界取「所有候选的最小值」，而不是「第一个匹配的阶段」**
  - *原因*: 原来的探测器按 Stage1→2→2.5→3 顺序，**先匹配上的先返回**。三份样卷全部切晚了
    （广东晚 3765 字、江苏晚 2029 字、湖北晚 7985 字），因为最靠前的两个信号——
    无标题的答案键（`21—23. CBC`）和 `【21题详解】`——只有最后一个阶段才去找。
  - *后果*: 答案区留在了正文里，于是后面所有 section 起点都能落进答案区：
    广东的「应用文」段抓到的是答案里的范文，「读后续写」抓到的是范文的 Paragraph 1/2，
    而两道真作文题被吞进了「语法填空」。用户报的第 13/14/15 条其实是同一个 bug。
  - *做法*: 所有探测器只产出候选，取 `min()`。新增两个高精度探测器：答案键（题号区间 + 恰好等量的字母）
    和逐题解析标记。
  - *验证*: 三份卷的切点都精确落在「读后续写题干最后一行」与「答案键第一行」之间。

- **决策 7: 题干里出现答案 = structural，不是 cosmetic**
  - *原因*: `segment_quality` 原来**专门豁免**了作文两节的答案粘连（判为 cosmetic），
    所以 `needs_model_fallback` 永远是 False，坏切分一路畅通到学生版。
    这个豁免正是答案泄漏到学生手里的通道。
  - *做法*: 去掉豁免；答案键、`【N题详解】`、参考范文一律 structural（触发回退或直接停）。
    宁可停，不可把答案发给学生。

- **决策 8: 讲解按「每份卷一个多轮会话」跑，评分先暖缓存再并发**
  - *原因*: DeepSeek 的缓存是**自动前缀缓存**，不是「会话」——两次请求的 message 列表从头
    逐字节相同多远，就共享多远。16 个 worker 同时发车时谁也没暖到缓存（enrich 命中率只有 21%）。
  - *做法*: 同一份卷的题目在**一个 conversation** 里依次追问（前缀不断增长且全部命中）；
    卷与卷之间仍并行。评分保持无状态，但先串行打第一个调用把静态前缀写进缓存，再 fan-out。
  - *效果*: score 71% → **96%**，enrich 21% → **72%**。pro 的缓存命中价是未命中的 1/120，
    所以整轮成本仍只有约 $0.19。
  - *代价*: 上下文会增长；超过 200k token（1M 的 20%）自动开新会话，避免降智。

- **决策 9: thinking 打开时，`max_tokens` 必须覆盖「思考 + 回答」**
  - *原因*: 推理 token 计入输出配额。把 thinking 默认打开后，1200 的评分上限被思考吃光——
    实测有一次调用 `completion=1200 / reasoning=1198`，**只剩 0 个 token 写 JSON**。
    JSON 被截断 → 解析失败 → 旧代码静默存成 `raw_score` → 下游读不到分数 → 该题按 0 分排序。
  - *做法*: 上限按「思考 + 回答」重新定尺（score 4000 / review 6000 / enrich 8000 / vocab 16000）；
    解析失败不再静默降级，`require_parsed()` 直接报错并说明是被 max_tokens 截断。
  - *另注*: 词汇抽取是「提取」不是「推演」，effort=high 会让模型一直想到把预算耗尽，
    因此 vocab 单独用 effort=medium。

- **决策 10: 清空一个带类型的元数据字段 = 破坏文档；要删就整个删掉**
  - *原因*: `scrub_metadata()` 把 `cp:lastPrinted` 置成 `""`，产出 `<cp:lastPrinted></cp:lastPrinted>`。
    它的类型是 dateTime——空字符串不是「没有日期」，是**一个非法的日期**，Word 因此报
    「发现无法读取的内容」。这是学生版/教师版报错的**真正根因**（书签悬空是同期的另一个真实缺陷，
    但修掉它并不足以让 Word 满意）。
  - *佐证*: 答案汇总版是用模板新建的、根本没有 `lastPrinted` 可清空，所以它从不报错——
    和用户「只有学生版/教师版报错」的观察完全吻合。
  - *做法*: 删除元素而不是置空；`validate()` 增加 `empty_typed_core_properties()` 闸门。

- **决策 11: OOXML 的属性容器是有序序列，不是集合**
  - *原因*: `CT_TblPrBase` / `CT_PPrBase` 规定了子元素顺序。`set_table_borders()` 直接 append，
    结果 `w:tblBorders` 排到了 python-docx 已写入的 `w:tblLook` 之后 —— 顺序非法。
    Pandoc 生成的模板同样有 `keepNext`/`pageBreakBefore` 错位、`pgMar` 缺 `gutter` 的问题。
  - *做法*: 按 schema 顺序插入（`TBL_PR_ORDER`）；`blank_template()` 用 `normalize_template_ooxml()`
    修正模板自带的顺序与缺失属性。

- **决策 12: Word 兼容性问题一律用「真 XSD + 错误类型差集」定位，不靠猜**
  - *原因*: 包级检查（Content_Types / rels / 命名空间 / 书签配对）全部干净时，文件依然可能被 Word 拒绝。
    前两轮各花了很久在启发式排查上。
  - *做法*: 用 ECMA-376 的 XSD 校验**每一个 part**，然后把我们输出的错误类型集合减去
    「Word 能正常打开的文件」（原卷 + Word 修复版）的错误类型集合。差集就是真凶。
    原卷自己也有几百条 schema 报错（Word 容忍扩展），所以只能比种类、不能比数量。
  - *固化*: 打包脚本的 `--selftest` 现在会真的建一份 docx（含表格 + scrub_metadata）并跑 `validate()`，
    冻结包里跑不过就不出 DMG。

- **决策 13: 教师讲解版 = 原题 + 官方答案与解析 + AI 逐题解析**
  - *原因*: 老师讲题最需要的是「为什么选 D、为什么不选 B、原文定位在哪」，而旧版教师版给的是
    评分/词汇/语法/长难句——那是**备课资料**，不是**讲题内容**。原卷其实自带逐题解析
    （`【导语】` + `【N题详解】`），但流水线把整个答案区当泄漏源整段丢掉，只留了答案字母。
  - *做法*: 每题产出 3 段（2 个 docx part）：原题克隆 → 官方解析克隆 → AI 解析（notes）。
    原来的词汇/语法/长难句全部移除——学生词汇表本来就走独立的 `vocab` 阶段，教师版不必重复。

- **决策 14: `explain` 阶段取代 `enrich`，而不是并列**
  - *原因*: 教师版只剩三段后，`enrich` 产出的词汇/语法/长难句**没有任何消费者**了。
    留着它就是每轮白花一次 API 钱。
  - *做法*: `run_stage1` 与 GUI 的阶段链把 `enrich-selected` 换成 `explain`。
    `enrich-selected` 模式本身保留，可手动调用。

- **决策 15: 官方解析按「块归属」定位，不按字符区间切**
  - *原因*: 先写的字符区间版本在三份真实试卷上全崩。`DocxDoc.body_range()` 会把**任何与区间
    重叠**的块算进来，而天然的边界（下一组的答案串行 `24—27 DBDA`）常常和上一组最后一句
    **共处同一个 `w:p`**——相邻题组因此共用一个块而串题；原卷一旦停止讲解，区间还会一路
    吃进后面的参考范文。
  - *做法*: 顺序扫描答案区的每个段落，问「这一段在解释哪道题」。答案串行/分节标题/范文标记
    使当前题号归零；**只有含中文的段落**才归给当前题（这一条把英文范文挡在解析外）。
    实测：3 份卷 21 个题组全部连续、无串题。
  - *闸门*: 区间内若混进别的题型号段的块 → 返回空。宁可标「原卷未提供逐题解析」，
    也不能印错题的解析。
  - *容错*: 号段外的孤立笔误（湖北把 `【34题详解】` 写成 `【14题详解】`）只告警不拦截——
    它确实在本篇的连续区间里，扔掉反而会丢掉第 34 题的解析。
  - *另一个坑*: 题号**必须**取自题型的固定号段，不能取自 `answer_key`。江苏的语法填空答案
    连写成 `58. 59. to`，解析器因此没解析出 59；用这份残缺的题号集去要解析，第 59 题的
    （位置完全正确的）解析块就成了「别人的题」，把整篇正确的区间也一起否决了。

- **决策 16: 逐题解析的 prompt 存成 `prompts/*.md`，不是 Python 字面量**
  - *原因*: 讲题风格是要反复调的，而且该由懂教学的人调，不该每次都改 Python。
  - *做法*: 六个模板（阅读/七选五/完形/语法填空/应用文/读后续写）+ 一份公共风格头 `_style.md`，
    占位符用 `{{NAME}}`（模板里有大量 JSON 花括号，`str.format` 会炸）。
    路径走 `bundle_paths.prompt_dir()`；打包必须 `--add-data "prompts:prompts"`，
    `--selftest` 会把六个模板全部载入一遍，冻结包里少一个就不出 DMG。
  - *写作题的两个真实教训*（首轮实测）:
    1. **词数必须以题目要求为准**。prompt 里写死「100–120 词」，而湖北卷要求 80 词、
       读后续写要求 150 词——范文直接超标，超字数是实打实的扣分项。
    2. **不许在 JSON 字符串里用英文双引号**。模型写英文范文时自然会引用
       （`like "accept your feelings" helped me`），一个没转义的 `"` 让整份输出非法。
       解析器**不做静默修补**（修出来的范文会被悄悄改坏），而是让模型自己重发一次：
       会话内前缀命中缓存，几乎不花钱；再错才硬失败。

- **决策 17: 默认「速度优先」（flash），出成品才切「质量优先」（pro）**
  - *原因*: pro 跑一轮 ¥1.35，flash ¥0.41。改一行 prompt 就要重跑的阶段，贵到不敢重跑
    就等于没法迭代。
  - *做法*: `scripts/model_presets.py` 一处定义两档，CLI（`--preset`）和 GUI 共用，
    避免「加一个模型要改三个文件」。单项 `--explain-model` 等仍可覆盖 preset。
    切分不进 preset——它本地跑、不花钱，模型只是异常卷的回退。

- **决策 18: 分步重跑——每个按钮把下游一起带上，`--force` 只落在被点的那一个阶段**
  - *原因*: 老师真实的用法是「选题还行，但词汇表不满意」。而在此之前只有一个「开始整理」，
    而且它给 segment 阶段无条件加了 `--init`（＝`shutil.rmtree` 整个输出目录），所以
    「只重做一块」在结构上就不可能。
  - *真 bug（已修）*: `select` / `review-select` 都会覆写 `selected_items.json`。换了选题后：
    新题**没有解析**，`export-docx` 照样导出（教师版那一篇是空的，无任何警告）；
    `vocab_index.json` 只有 `run_vocab` 会重写，所以词汇表**还是上一批的词**——而那是发给学生的。
  - *做法*: `Job(stages, force, init, reselect)`。改变「选了哪些题」的按钮（重新切分/评分/选题）
    必须把 explain/vocab/export 一起带上；下游**不加** `--force`，于是逐题缓存让「只为新题花钱」
    自动成立。再加 `assert_selection_is_complete()` 作为导出前的闸门，缺解析/词表过期一律停下。

- **决策 19: 「换一批题」必须走 AI 复核，并且要明说「这批不满意」**
  - *原因*: `run_select` 是纯本地确定性排序（无 API、无随机），重跑它得到**逐字节相同**的选题。
    而即便走 `review-select`，同样的评分喂给同样的模型，也多半原样再选一遍。
  - *做法*: `--reselect` 把上一轮的 item_id 塞进 prompt（「老师对这批不满意，请尽量换一批」）。
    候选池太小时（3 份卷＝每个题型只有 3 个候选、要选 2 个）明确告诉用户「最多只能换掉一道」。

- **决策 20: 一份 `usage.jsonl` 账本，写在调用发生的地方**
  - *原因*: 原来的计价要事后扫 `scores/`、`explanations/`、`vocab/` 里嵌的 usage，再去
    `api_conversations/*.md` 里 **grep 模型名**。于是：关掉「保留中间产物」后一律按 pro 计价
    （flash 跑一轮被高估约 3 倍）；`segment` 和 `review-select` 没有逐题目录，**花的钱根本没被算**。
  - *做法*: `record_usage()` 在 `call_stage_model` 里每次调用追加一行（stage/model/token 三分/耗时）。
    计价、分阶段×模型明细、以及时间预估所需的耗时，全部从这一份文件读。旧 run 回退到老的扫描逻辑。

- **决策 21: token 数用 DeepSeek 自己的分词器，不再 `len // 3`**
  - *原因*: `len(text)//3` 对中文**低估约 40%**、对英文**高估约 40%**。用它报价等于没报。
  - *做法*: 只装 `tokenizers`（纯 Rust 轮子，`pip install --no-deps`——它的
    `huggingface-hub/httpx/tqdm` 依赖只有 `from_pretrained()` 才用得上），读仓库里自带的
    `assets/deepseek_tokenizer/tokenizer.json`（7.5MB）。**拿不到就退回字符估算，绝不崩**——
    这是个花费显示，不该让一次打包疏忽毁掉整轮运行；所以 `--selftest` 里显式断言它在冻结包里能加载。

- **决策 22: 预计时间按「秒/单位」学，按 (stage, model, effort, thinking) 分桶**
  - *原因*: 旧的 ETA 把每个阶段**等权**（`i / total`）。切分是本地的、一秒跑完；解析要几分钟。
    于是进度条开跑就跳到 11% 然后一动不动，早期的「预计剩余」离谱到没法看。
  - *做法*: `run_timing.py` 存最近 20 次的「秒/单位」（切分按试卷数，评分/解析/词汇按题数），
    取**中位数**（一次被限流的 429 长跑不能污染估算）；没有历史就用内置先验（flash 比 pro 快、
    thinking 和 effort 各有系数）。跑完就把实测写回去——「越多次越准」。进度条按各阶段的**预估耗时加权**。

- **决策 23（推翻 决策 16 里的词数改动）: 作文范文按 100–120 / 150–180 词写，不按题目标注的词数**
  - *原因*: v0.5 我把它改成「以题目要求为准」（湖北卷标 80 词、续写标 150 词）。
    **与多位一线老师讨论后确定：满分范文要写得比考纲的最低词数丰满**，才示范得出「要点齐全 + 语言有亮点」，
    续写也才铺得开环境/动作/心理三个维度。**不要再改回去。**
  - *附带*: 词数由 `essay_word_count()` **本地数**，不读模型自报的 `词数`（它经常漏填），
    并且要**排除称呼与落款**——考纲的词数要求本来就不含它们，含进去的数字会在老师判断
    「是不是写超了」的那一刻误导她。

- **决策 24: HTTPS 走 macOS 钥匙串（`truststore`），不走 Python 自带的 CA 列表**
  - *原因*: 老师在**一台新电脑**上装好后，API 测试就过不去：
    `[SSL: CERTIFICATE_VERIFY_FAILED] self-signed certificate in certificate chain`。
    这不是密钥问题、不是 DeepSeek 的问题。「证书链里有自签证书」= 那台机器上有东西在**中间拆 TLS**
    （学校/公司代理、杀毒软件、VPN）。这些产品把自己的根证书装进 **macOS 钥匙串**并重签每一条 HTTPS：
    Safari 没事，因为它问系统；**Python 不问系统**，它抱着自己的 CA 列表，于是链子断在一个它没听说过的根上。
  - *做法*: `net_tls.install()` → `truststore.inject_into_ssl()`，**在进程最开头**调（`app/main.py` 与
    pipeline 的 `main()` 都要，且必须早于任何 `ssl` 使用）。这样验证走 macOS Security 框架，
    那个拦截根系统本来就信，于是通了。
  - *certifi 不是替代品，只是兜底*: Mozilla 的列表里**没有**企业根证书，救不了拦截这种情况；
    它只覆盖「打包时压根没带 CA 列表」这另一种毛病。
  - *最后的退路*: `--insecure-ssl` / 调试模式里的复选框（默认关）。有些网络的根证书压根没进钥匙串，
    那时这是唯一出路（`curl -k`、`pip --trusted-host` 同理）。
  - *闸门*: `--selftest` 里断言 `net_tls.mode() == SYSTEM`——打包漏掉 truststore 会**静默**退化成
    certifi，而 certifi「看起来能用」，直到换一台电脑就废。冻结包必须自证走的是钥匙串。
  - *测不到的部分要说实话*: 本机复现不了中间人环境。测试只能证明「未知根仍被拒绝」和
    「验证确实委托给了 OS」；真正的验收是老师在**那台电脑**上再点一次「测试」。

- **决策 25: 取消 = 把连接拆掉，不是设个标志位**
  - *原因*: 原来只在**阶段之间**查一次标志。解析跑到一半按取消要等好几分钟；429 退避里还可能
    `time.sleep()` 90 秒，谁也叫不醒——按了跟没按一样。
  - *做法*: `CANCEL` 事件 + `Cancelled` 异常，检查点铺到每份卷、每道题、每一轮、每次发请求之前；
    退避从 `time.sleep()` 换成 `CANCEL.wait()`。
  - *关键坑（测试抓出来的）*: worker 阻塞在 socket 读上时，**`close()` 唤不醒它**——close 只是丢掉
    本线程的句柄，另一个线程仍卡在同一个 fd 的 `recv()` 上。必须先 `sock.shutdown(SHUT_RDWR)`
    把连接从底下拆掉，那个读才会立刻抛错。为此把 `call_chat_completion_http` 从 `urllib.urlopen`
    改写成 `http.client.HTTPSConnection`（顺便这也正好是装 SSL context 的地方）。
  - *不许撒谎*: DeepSeek **没有**「停止生成」接口（非流式请求只能断连）。所以确认框如实写明：
    已生成的题目会保留、正在生成的作废、**已发出的请求可能仍计入用量**。

- **决策 26: `reasoning_effort` 只有 high / max（其余三档是摆设，删掉）**
  - *原因*: [官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)：取值 `high`/`max`，默认 `high`，
    **`low` 和 `medium` 被映射成 `high`**，`xhigh` 映射成 `max`。
    我们原来的四档 `none/low/medium/high` 在服务端**完全等价**——那个强度滑块是装饰品，
    而「速度优先 = 强度 medium」根本没省下任何东西（真正起作用的只有 flash 这个模型选择）。
  - *做法*: `EFFORTS = ["high", "max"]`，旧值自动归一（`normalize_effort`）；界面从滑块改成二选一。
  - *`max` 必须配更大的 `max_tokens`*: 思考链很长，而推理 token 计入输出配额（决策 9 的老坑）。
    `effective_max_tokens()` 在 `parse_args` 里一次性放大，**同一个数字**同时喂给请求和
    `require_parsed()`——只在客户端放大会让截断检查拿旧上限去比，把正常回复判成截断。
  - *质量优先只在「老师会读到的东西」上用 max*: 解析 + 复核选题。评分是轻量筛选；
    词汇表是抽取不是推理——决策 9 记着它会一路想到把预算耗光、一个 JSON 都吐不出来。
    （顺带戳破：当年用 `medium` 去「限制」它其实毫无作用，因为 medium ≡ high。真正救它的是 token 上限。）

- **决策 27: 给模型讲引号规则，必须把「语法符号」和「字符串内部」分开说**
  - *原因*: 我原先只写「JSON 字符串里不要用英文双引号」。flash 把这条**应用到了 JSON 的语法本身**，
    输出 `{“word”: “abandon”}`——中文引号当分隔符，整份非法。更糟的是纠正回合的措辞
    **又说了一遍同样的话**，于是它又犯了同样的错。vocab 阶段真的挂在第 9 项。
  - *做法*: prompt 里两条分开讲，并给正反例；`_repair_instruction()` **按实际犯的错**选纠正话术
    （检测到中文引号 → 明确说「语法符号被写成了中文引号」，并给出正确/错误示例）。
    一句泛泛的「你输出的不是合法 JSON」只会换来同样的回复。

- **决策 29（已被决策 33 修正一半）: 词汇表读「整卷正文」，不再一题一问；缓存键从题号变成卷名**
  - ⚠️ **「不再」这两个字是错的。** 分块那条路仍然有它的道理，现在由老师二选一（决策 33）。
    下面记的是整卷这条路的做法与代价，它现在是**默认**，但不是唯一。
  - *原因*: 旧版只喂被选中的 18 道题的 `segment_body`，一题一问。模型看不到整卷，
    判断不了「这个词在**这份卷子**里到底算不算重难点」——而这恰恰是我们要它做的判断。
  - *做法*: 读 `<out>/extracted_text/<stem>.txt`（切分阶段本来就每次都写）。卷间并行、
    卷内一个 `Conversation`。按 token 预算切块：**1M 上下文的模型上恒为 1 块**
    （40% = 336k，而一份真卷只有 8–13k token），切块只在小上下文的 provider 上才起作用；
    真要切了，最后在同一会话里追加一轮「合并去重 + 排序」（前缀命中缓存，几乎不花钱）。
  - *必须去掉答案区*: `extracted_text` 是**整个 docx**，含答案键和参考范文。词汇表是**学生版**。
    旧的按题提问是靠 `segment_body` 天然避开的，改成整卷后必须显式调
    `trim_answer_tail_from_text()`（决策 6 的边界）。实测三份卷砍掉 43–59% 的文本。
    两个理由，第二个最容易漏：① 答案绝不能进学生版；② 答案区里有**参考范文**——
    那是学生手上那份卷子里**没有**的文本，从里面提的词是从他读不到的文章里提的。
  - *连带推翻决策 18 的一半*: 词表现在按卷缓存（`vocab/<卷名>.json`），
    **换一批题不再让词表过期**——词本来就是整卷的，卷没变。所以「重新选题」按钮不必再带上 vocab，
    `assert_selection_is_complete()` 也从「每道选中的题都要在词表里」改成
    **「每份贡献了选中题的卷都要有词表」**。它仍然拦得住真正的新卷进入选题。
  - *代价（已和用户确认）*: 学生词表里会出现「他手上那份卷子没有的题」的词。换来的是模型能看到全文语境。

- **决策 33（修正决策 29 的一半）: 整卷 vs 分块不是对错问题，是教学取舍——交给老师选**
  - *原因*: 决策 29 把词汇表从「逐题分块」单方面改成了「整卷」，理由是模型看不到全文就判断不了
    「这个词在这份卷子里算不算难」。那个理由是对的，但它**不是全部**：
    - **分块**只读学生手上真有的那 18 道题 → 词表和他的卷子**逐题对应**，一个字都不多。
      代价是模型一次只看一道题，缺全文语境。
    - **整卷**能通读全卷做判断 → 判断更准。代价是词表里会有**学生那份卷子里没有的题**的词。
    哪个更好取决于老师怎么用这张纸，**不该由代码替她决定**。所以两条路都留着，
    基础模式给一个二选一（**完整=分块 / 困难=整卷**），默认 **困难（整卷）**。
  - *闸门必须问词表、不能问命令行*: 老师可以拨了开关但没重跑 vocab 就去导出。
    `assert_selection_is_complete()` 读 `vocab_index.json` **每行自带的 `vocab_mode`**：
    - `chunked` → 每道选中的题都要在词表里（换题就过期，必须重跑）
    - `whole` → 每份贡献了选中题的卷都要有词表（换题**不**过期，决策 29 的结论保留）
    拿当时的 `--vocab-mode` 去判，会用分块的规矩去卡一份完全合格的整卷词表。
  - *老词表按「形状」认模式*: `vocab_mode` 这个字段是这次才加的，盘上已有的词表没有它。
    统一默认成某一种会**认错一半**，所以看形状：有 `item_id` 的是分块，没有的是整卷。
  - *缓存分目录*: `vocab/chunked/<题号>.json` 和 `vocab/whole/<卷名>.json`，
    免得一种模式跑到一半的结果被另一种静默复用。
  - *截断警告只对整卷报*: 38,934 那个实测峰值是**通读整卷**读出来的；
    分块一次只喂一道题，输出小得多（实测单次最大 17,827）。对分块也报，
    只会训练老师忽略唯一重要的那条警告。
  - *实测对比（三份样卷，flash + 最深档，都没截断）*：

    | | 完整（分块） | 困难（整卷） |
    |---|---|---|
    | 调用数 | 18 | 3 |
    | 输出 tokens | 203,251（思考 92%） | 76,223（思考 94%） |
    | 花费 | **¥0.44** | **¥0.15** |
    | 实际耗时 | ~13 分钟 | ~6 分钟 |
    | **产出词数** | **234 词 / 202 词形** | **104 词 / 73 词形** |
    | 缓存命中 | 68% | 99% |

    **「完整」名副其实**：词是整卷的 2.25 倍。代价是贵 2.9 倍、慢一倍
    （逐题问 = 每道题都要重付一次深度思考，而且卷内前缀缓存命中只有 68%）。
    这就是那个取舍本身——**没有更好的一个，只有更适合她这张纸的一个**。

- **决策 30: 模型/档位不再写死 DeepSeek——`providers.py` 一张表描述每家 API**
  - *原因*: `chat_payload()` 无条件写 `reasoning_effort` + `thinking:{type}`，这两个字段只有 DeepSeek 认。
    发给 OpenAI 会被拒；GLM/Qwen 会**静默忽略**（它们的开关叫 `enable_thinking`，而且**必须走
    `extra_body`**，当普通关键字传给 OpenAI SDK 会被悄悄丢掉，模型就不思考了，还没人报错）；
    Claude 连协议都不是 chat/completions。
  - *做法*: `ProviderSpec.thinking_style` 是唯一真正不兼容的地方（deepseek/openai/zhipu/qwen/anthropic/none）。
    `request_fields()` 返回 `(standard, extras)`：extras 是非 OpenAI 标准的厂商扩展，
    走 HTTP 时并进 body，走 SDK 时必须放 `extra_body`。
  - *档位自适应*: preset 只说「快/强」和「标准/深度」两个**角色**，由 provider 解析成它**真实存在**的档位。
    DeepSeek 的深度是 `max`，OpenAI/Claude 是 `xhigh`，**GLM 根本没有强度维度**——
    界面就如实显示「不可调」，而不是画一个不起作用的开关（决策 26 骂过的正是这个）。
  - *Claude 不走 OpenAI 兼容层*: 官方明说它不支持 extended thinking 和 prompt caching，
    而这两个是本项目的命脉（决策 8：缓存命中价是未命中的 1/120）。所以是原生 `/v1/messages` adapter，
    但**复用同一个 `post_json`**——取消（决策 25 的 `SHUT_RDWR`）和钥匙串校验（决策 24）
    是靠「绕不过去」保证的，不是靠下一个人记得再接一遍。
  - *上下文不明的模型一律往小了猜*: 猜小了只是多切一块（正确，略啰嗦）；猜大了会撑爆上下文、整轮作废。
  - *价格不知道就说不知道*: `ModelSpec.price=None` → 报「未配价格，未计入」。
    旧代码 `PRICES.get(model) or PRICES[DEFAULT_MODEL]` 会按 pro 给未知模型计价——决策 20 骂过，
    flash 跑一轮被高估 3 倍。model id 会下架换代（GLM 4.6/4.7 已于 2026-07-09 下架），
    所以「刷新模型列表」（`GET /v1/models`）是必需品，不是锦上添花。

- **决策 31: 两个 preset 都用「该模型最深的那档」，包括 vocab（明知会重踩决策 9 的坑）**
  - *原因*: 用户明确要求「速度优先全部默认 flash max，质量优先全部默认 pro max」。
    preset 选的是**模型**，不是思考量。
  - *和决策 9 的冲突*: 决策 9 记着 vocab 放开思考会把 token 预算全烧在思考上、一个 JSON 都吐不出来
    （真的挂在第 9 项）。当时的「修复」是把 effort 钉在 medium——而决策 26 后来证明 medium ≡ high，
    那个修复从来就没生效过；**真正救它的是 token 上限**。
  - *做法*: 护栏从「限制 effort」换成「放大 output」。`effective_max_tokens()` 在**任何**阶段跑到
    「该模型最深的一档」时把上限 ×3（并 clamp 到模型的 max_output）。
    「最深」**不是字符串 `max`**——OpenAI/Claude 的深度档是 `xhigh`，思考链一样长；
    拿 `"max"` 去字符串比较，会让这两家在深度 preset 下用**浅档的 token 上限**，那就是决策 9 换了张皮。
    改用 `providers.is_deepest()` 问 provider。
  - *实测（三份样卷，flash + max）*：**94% 的输出 token 是思考**（87,395 / 92,853）。
    单次最差 **38,934 输出 / 37,022 思考**，只用约 1,900 token 写 JSON，耗时 354s。
    对照组 flash + high：输出 17,188（思考 66%），耗时 192s，**词数几乎一样（114 vs 116）**。
    也就是说 max 花了 5.4 倍 token、4.3 倍时间、3.8 倍的钱，换来同样长的词表。
    两次选词只重合 32%——不是「max 更好」，只是这个任务本来就有主观性。
  - *因此上限按实测定尺*：`--vocab-max-tokens` 从 16000 提到 **22000**（×3 正好顶到
    `MAX_EFFORT_TOKEN_CEILING` 64,000），对实测最差值留 39% 余量。
    **16,000 的老上限下，这三次调用会全部截断。**
  - *兜底*: `require_parsed()` 在被截断时**硬失败并说明原因**，不会静默存半张词表。
    报错会按**这个模型真实存在的杠杆**来说话——GLM 没有强度档，就不能叫人去「降一档」。
  - *已知风险（会提前警告）*: GLM（输出上限 32k）和 Qwen（32,768）的**输出上限低于实测峰值 38,934**，
    深度档下可能截断。`run_vocab` 开跑前就会警告并告诉你该拧哪个旋钮，而不是四分钟后才失败。
  - *真要再出截断，就把 vocab 钉回标准档*——`test_both_presets_think_as_deeply_as_the_model_allows`
    就是那个开关，`test_vocab_has_real_headroom_over_the_worst_measured_call` 守着那个数字。

- **决策 32: PDF 后端可选 MinerU（官方云 API），与 PaddleOCR 共用同一条下游**
  - *原因*: 只有 PaddleOCR 一条路，而它按账号部署、要老师自己去控制台找 URL。
  - *做法*: 两个后端都产出同样的 `OcrBlock` 列表，都走 `blocks_to_docx` —— 排版完全一致，
    下游根本不知道有两个。
  - *结构上的差别*: **MinerU 是异步的**（提交 → 轮询 → 下载 zip → 读 `content_list.json`），
    PaddleOCR 是一次阻塞 POST。轮询循环必须可中断：`sleep` 是注入的，走 `_sleep_or_cancel()`，
    否则老师按取消会卡在轮询里直到 MinerU 解析完。
  - *否决的做法*: MinerU 支持 `extra_formats:["docx"]` 直接产出 docx。但那份 docx 的样式表不是我们的
    `student_reference.docx`，`docx_splice` 依赖的 note 样式不存在——正好撞上「引用未定义样式」
    这个历史事故根因。

- **决策 28: 界面文案不谈钱，但跑完的花费读数保留**
  - *原因*: 满屏的「不重复花钱」「便宜快」「更慢更贵」「不花钱」，本意是让老师放心用，
    读起来却像在提醒她「小心，这玩意烧钱」。
  - *做法*: 静态文案里的金钱框架全部拿掉（有测试守着，防止写回去）；
    跑完之后 `usage_report.summary_line()` 那一行**照常显示**——那是她要的事实，不是劝退的框架。
